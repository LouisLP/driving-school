# i18n

## The convention

**A folder owns its own strings.**

```
src/features/students/i18n/en.json   ->  t('students.…')
src/features/students/i18n/de.json
src/shared/i18n/en.json              ->  t('shared.…')
src/shared/i18n/de.json
```

One rule, no exceptions: **`<owner>/i18n/<locale>.json` puts its keys under `<owner>.`**.
The namespace is the folder name — there is no registry, no manifest, nothing to
import. `import.meta.glob` in `messages.ts` picks the files up.

Adding a feature therefore means: create `src/features/<name>/i18n/en.json` and
`de.json`, and use `t('<name>.…')`. That's the whole onboarding.

Strings used by more than one feature go in `src/shared/i18n/` under `shared.`.
Everything else stays with its feature, even if it looks generic — duplicated
wording is cheaper than a shared bucket nobody can safely change.

## Translating

```vue
<script setup lang="ts">
import { useT } from '@/i18n/use-t'

const t = useT()
</script>

<template>
  <h1>{{ t('students.list.title') }}</h1>
  <p>{{ t('students.list.count', students.length) }}</p>
</template>
```

Use `useT()`. Do **not** use `useI18n().t` or the global `$t`: vue-i18n types
those as `(key: string)`, so the typed schema only powers autocomplete there and
a typo compiles fine. `useT()` narrows the key to `MessageKey`, which makes a
misspelled or stale key a build error.

`MessageKey` is also the right prop type when a shared component takes a label
from its caller: `defineProps<{ labelKey: MessageKey }>()`.

For anything that is not a message key — `n()`, `d()`, the current locale —
use `useI18n()` from vue-i18n directly.

## English is the source of truth

`en.json` defines the key set. The typed schema is generated from the `en.json`
files only (`locale-messages.generated.d.ts`, regenerated by the Vite plugin on
dev/build and by `pnpm i18n:types`). It is committed so `vue-tsc` works
standalone; if it looks stale, run `pnpm i18n:types`.

Write the English key first, then the German one.

## A missing German string

Three layers, loudest last:

1. **Runtime:** falls back to the English string. Users never see a raw key.
2. **Dev:** vue-i18n warns per lookup, and `reportMessageDrift()` logs every
   missing (and every stale) key once at startup.
3. **CI:** `diffMessageKeys()` is asserted empty in
   `src/i18n/__tests__/messages.spec.ts`. A missing translation fails the build.

So: never silent, but never broken either.

## Adding a locale

Add it to `SUPPORTED_LOCALES` in `locales.ts` and drop `<locale>.json` next to
every existing `en.json`. A locale file whose name is not in `SUPPORTED_LOCALES`
throws at startup rather than being silently ignored.

Locale switching, persistence and date/number formatting are not settled yet
(see the "Locale detail" item on issue #1).
